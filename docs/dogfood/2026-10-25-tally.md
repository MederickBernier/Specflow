# Dogfood: building `tally` with `specflow run`

Task: `task-run/T11`. Date: 2026-10-25. Specflow at `1c835bd`, Claude Code 2.1.310, model Haiku.

## Setup

- A new sandbox repo for **tally**, a `wc`-like CLI (Node 24, TypeScript by type stripping, `node:test`, no dependencies).
- `specflow init`, then hand-written steering files and one feature, `count`: 5 approved requirements (one file, several files with a total, stdin, `-l/-w/-c` flags, missing files) and 5 tasks, one per requirement.
- `config.yml`: `commit.mode: staged`, `extraArgs: ["--model", "haiku", "--allowedTools", "Bash(node --test:*)", "Bash(node src/cli.ts:*)"]`.
- Every line of code came from `specflow run count/T<n>`. After each run a human-style review of the staged diff and tests, then `git commit -F .git/SPECFLOW_MSG`.

- 5 of 5 runs succeeded on the first try. About 2.7 minutes of run time and roughly $0.05 in total.
- `lint` stayed clean, every task ended `done`, every commit carries correct trailers, and `trace` answers per requirement.
- The staged-review flow felt right: one diff per task, one prepared message, commit by hand.
- One specflow bug found and fixed on the way (`1c835bd`): when the agent edits `tasks.md` itself, the file was recorded twice ("Staged 8 files" for 7).

## What hurt, most important first

### 1. Scope creep breaks traceability

In T1 the agent also wrote T5's missing-file handling ("That's really T5 scope. Keep it or strip it back"), despite "Work on this task only". T5 then only added a test. Result in `trace count/R5`: one commit touching `test/cli.test.ts`; the code that implements R5 (`src/cli.ts`) is attributed to `R1`.

This is the most important finding for `drift-check`: its touched set for R5 will miss the file that implements it, so a later change to that code will never be flagged against R5. Trailers record intent, not what the code actually does.

Proposals:
- After a run, warn when changed files fall outside the task's `files:` list (cheap, deterministic, fits "flag, never rewrite").
- Name the other open tasks in the prompt as out of scope, so the agent knows where the boundary is.
- Design `drift-check` assuming attribution is incomplete; do not rely on the trailer touched set alone for "unimplemented".

### 2. The agent's spec feedback has nowhere to go

The agent found a real spec bug (`node --test test/` fails on Node 24; the steering said to use it) and filled a spec gap on its own (unknown flags print an error and exit 2, which R4 never specified). Both survive only in the run log and the commit body. The prompt forbids editing `.specs/`, which is right, but nothing replaces it.

Proposal: ask the agent to end with a short "Spec notes" section, and have `run` print it separately after the result ("The agent suggests these spec changes"). Humans then decide, per the principle.

### 3. Status ownership is confusing

The agent edited `tasks.md` to set its own status in 5 of 5 runs, and each time noticed it was already `doing` ("It was `doing` in the working tree, not `todo` as the task block said"). Specflow sets the status anyway, so the agent's edit is redundant and costs a turn.

Proposal: specflow owns the status line. Change the prompt to "Do not edit files under `.specs/`; specflow updates this task's status", and drop the exception.

### 4. Compound shell commands are denied

9 denied Bash calls across 5 runs, almost all `a; b` or `a && b | c` where each part alone was allowed. Each costs a turn and a retry. Claude Code matches permission rules against the whole command.

Proposals:
- Prompt: "Run one shell command per call."
- README: document how to allow the project's test command, with examples (this is also issue 6).

### 5. Commit bodies are the agent's whole final reply

Bodies were 13 to 17 lines of chat-style markdown ("Files:", "Choices I made:"), useful in the terminal, noisy in `git log`.

Proposal: use the first paragraph as the body, or no body, and keep the full reply in the run output only.

### 6. Allowing test commands means Claude-specific flags in config

`extraArgs: ["--allowedTools", "Bash(node --test:*)", ...]` works but leaks harness syntax into the spec config, and a new user has to know Claude Code's permission rule format. Without it (the T10 run) the agent cannot verify its work at all.

Proposal: document it in the README now; later consider `harness.claude-code.allowedTools` as a typed setting, and a `harness check` warning when no Bash rule is configured.

### 7. Usage numbers mislead

Every run printed `$0.01` (rounded to cents) and 300k to 560k "tokens in", because cache reads are counted as input. A tiny task looks expensive and every task looks the same.

Proposal: show cost with three significant digits under $1, and report cached input separately (`event.usage` could gain `cachedInputTokens`).

### 8. Minor

- `specflow init` creates an `example` feature that has to be deleted by hand before writing a real one. Acceptable for a first run; a `--no-example` flag would help.
- R1's example numbers in the spec (2 lines, 5 words, 24 bytes) had to match a fixture the agent wrote; it did, but only because it checked with `wc`.

## Before starting drift-check

- Decide 1, 2, 3 and 5: they change the `task-run` prompt and recorder (`task-run/R3`, `R6`, `R7`), so they are spec changes first.
- Write `drift-check`'s design with finding 1 in mind.
- 4, 6 and 7 can wait for the README (`vscode-extension/T11`) and a usage tweak.
